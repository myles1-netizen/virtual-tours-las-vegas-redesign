# Lessons Learned — Real Bugs Found This Build (Don't Repeat These)

Everything below was an actual bug found and fixed during development, not a style preference. Read this before touching layout, color, or content-authoring patterns — several of these are subtle and easy to reintroduce.

## Contrast / readability bugs

1. **`--brass` (`#B08D57`) fails contrast with white text (~3:1, needs 4.5:1 for AA).** It's fine for small accent text/labels/borders on the paper background, but NEVER use white text on the plain `--brass` background for buttons. Use the dedicated `--brass-btn` (`#8A6A3C`) / `--brass-btn-2` (`#7A5E34`, darker on hover/press) tokens instead — verified ~5:1 and ~6:1 contrast respectively.
2. **CSS specificity bugs silently override intended colors.** A generic `.brass { color: var(--brass) }` utility class (for text accents) was unintentionally overriding a more-specific-looking `.btn.brass { color: white }` rule because Divi/CSS cascade rules don't work the way "more words in the selector = wins" intuition suggests — always check computed styles in a real browser, don't just read the CSS and assume it applies.
3. **Text directly over photos needs a guaranteed-contrast mechanism, not a gradient overlay tuned per-image.** Early versions used a dark gradient behind hero text, which broke whenever a particular photo was too bright/light-colored in the wrong spot (e.g. a white 3D-render image used as a hero background made white text nearly invisible). The fix that actually holds up: a **solid, semi-opaque panel** (`rgba(15,14,12,0.66-0.72)` + `backdrop-filter: blur`) behind text blocks that sit on photos, so contrast is guaranteed regardless of the image underneath. Apply this pattern to any new hero/banner treatment.
4. **`Astro`/JSX component prop strings should never contain literal `&amp;`.** If a prop is a plain string like `title="X &amp; Y"`, the renderer double-escapes it and users see the literal text "&amp;" on the page. Only use `&amp;` inside actual raw HTML content between tags (e.g. `<h3>X &amp; Y</h3>`); inside a JS string prop, just use a literal `&`.

## Layout bugs

5. **CSS Grid items with `grid-column: span 2` and a fixed `aspect-ratio` become both wider AND taller** than their non-spanning siblings in the same row, creating visible gaps (the row height is set by the tallest item, so shorter neighbors leave dead space below them). Fix: give wide/spanning items a proportionally wider aspect ratio (e.g. `8/3` instead of `4/3` for a 2-column span) so height stays constant across the row — don't just let width scale and expect height to stay put.
6. **A before/after image-reveal slider must render both images at identical scale.** A "counter-clip" CSS hack (forcing the clipped image to `width: 100vw` to "counteract" its shrinking container) actually blew the image up far larger than the frame, making it look zoomed in/cropped wrong relative to the other image. Correct approach: keep both images at a constant, identical size (`width/height: 100%; object-fit: cover` on both), and reveal/hide portions using `clip-path: inset(...)` on a wrapper — never resize the image element itself to control the reveal.
7. Any UI that defaults to a 50/50 split comparison (before/after, etc.) should have its default position tested against the actual images — a fixed default position can accidentally land right on/past the visually "recognizable" landmark in a wide photo, making a technically-correct comparison look like two unrelated images at a glance. Consider defaulting to mostly showing the more impressive "after" state rather than a strict 50/50.

## Data-accuracy bugs (the expensive one — audit before trusting any existing image/content mapping)

8. **A full portfolio image audit found ~13 of 26 entries had metadata that didn't match the actual image content** — including several files that were flat-out **logos or marketing graphics being displayed as if they were real property photos** (a VRBO/Airbnb logo graphic labeled as a rental interior photo, various vendor/client logos labeled as "as-built survey deliverables," a Matterport logo labeled as a "3D virtual tour"). Also found real photos with completely wrong alt text/category (a commercial office floor plan labeled "Henderson home exterior," a commercial building aerial photo labeled "living room with mountain views").
   - **Never trust a filename or existing alt-text/caption as ground truth.** Actually open and look at every image before using it or its metadata.
   - This kind of error is easy for an AI to introduce (plausible-sounding alt text generated without actually viewing the image) and easy for a human to miss on a quick skim. Do a deliberate image-by-image visual audit any time image data is inherited from a prior version of a project.

## Header/layout structural bug

9. A `position: sticky` header with a transparent background, intended to overlay a hero image, will NOT actually overlay anything unless the hero content has reserved space for it via padding/negative-margin — sticky elements still occupy their own space in normal document flow. This caused white header text to render against the plain page background (invisible) instead of the hero photo. Resolved by switching to `position: fixed` and reserving top padding on non-hero pages. **Simpler alternative adopted in the end: just make the header solid/opaque at all times** (`background: var(--paper)`, always) rather than fighting transparent-overlay-on-scroll complexity — this was also what the client explicitly asked for (white header background, not transparent or black) and is far more robust.

## Process lessons

10. When de-jargoning/humanizing AI-sounding copy, the actual "tell" is em-dashes (`—`) used as clause connectors in prose (e.g. "Mike shoots every property himself — the same photographer Zillow trusted..."). Decorative list-label dashes (e.g. "Multiple styles — modern, traditional, glam") and dashes inside meta `<title>`/`description` tags are fine and don't need touching.
11. Astro's `defineConfig()` in this version does NOT accept a function (only a plain object) — passing one silently breaks the whole config with no error thrown, resulting in every page rendering as an empty ~50-byte response. If dynamic config (e.g. different `base` path for dev vs. build) is needed, branch on `process.env.NODE_ENV` inside a plain object, not via a config function.
